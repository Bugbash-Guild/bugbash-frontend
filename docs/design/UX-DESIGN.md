# BugBash UX設計

現在のUXがどういう設計になっているか、どの枠組みに基づくかを記述する。
施策の履歴は `UX-IMPROVEMENT-PLAN.md`、デザイン正典との差分は `D1-IMPLEMENTATION-STATUS.md` を参照。

---

## 0. 採用している枠組み

| 枠組み | 用途 | 出典 |
|---|---|---|
| Job Stories | 要求の記述（`When [状況], I want to [動機], so I can [結果]`） | Klement / Intercom |
| 自己決定理論（SDT） | 動機の設計（自律性・有能感・関係性） | Deci & Ryan / NN/G |
| 過正当化効果 | 最大のリスク管理 | — |
| ダークパターン分類（時間/金銭/社会） | 倫理チェックリスト | Zagal et al. |
| Nielsen 10ヒューリスティック | 画面の点検 | NN/G |
| Progressive Disclosure | 情報設計 | NN/G |

**この製品の特殊事情**: 追跡対象がユーザーの**実際の開発活動**（PRのマージ）である。
そのため通常のゲームなら許容される仕掛け（ストリーク、ランキング、時限イベント）が、
そのまま**活動への圧力**に変わる。ダークパターン判定はゲームより厳しく取る。

**利用者は業務開発者に限らない**。個人開発・OSS・趣味のコミットも同じ土俵に乗る。
したがって「週末＝休むべき日」という前提は置かない。土日の活動はそのまま活動日として数える。
週末を途切れ判定から外したのは休息を強制するためではなく、
**平日だけ働く人が不利にならないようにする**ためである（BE #305）。

## 1. 前提（未検証の仮説として明示）

利用ログが存在しないため、以下は**仮説**である。実装判断はこの上に乗っている。

| # | 仮説 | 根拠 |
|---|---|---|
| H1 | ユーザーはBugBashに常駐しない。GitHubが活動場所で、BugBashは結果の確認先 | 製品定義（「そのまま冒険になる」） |
| H2 | 開く動機の大半は外部トリガー（マージ通知・同僚の言及） | H1からの演繹（未検証） |
| H3 | コインは意識せず貯まり、使われないまま積み上がる | **実データ**: 16,475コイン=未使用54回分の実例 |
| H4 | 課金の意思決定は「特定のモンスターへの愛着」から始まる | 正典の demand-first 原則（未検証） |

**検証方法**: チーム5人に15分ヒアリング（Job Storiesを読み上げて「この状況ある?」と聞く）で
H1・H2・H4 は潰せる。モバイル比率は User-Agent 集計で取れる。

## 2. Job Stories

```
JS-1  マージした通知を見たとき、何を得たのかすぐ知りたい。
      働いた成果が形になったと感じたいから。

JS-2  BugBashを開いたとき、いま自分にできることが1つ分かってほしい。
      眺めて閉じるだけの訪問にしたくないから。

JS-3  召喚を引いたとき、それが新種かどうか即座に分かってほしい。
      集まっていく実感が欲しいから。

JS-4  特定のモンスターに愛着が湧いたとき、その子を飾る手段を知りたい。
      自分の相棒として見せたいから。

JS-5  同僚が話題にしたとき、自分の立ち位置と見せられるものを確認したい。
      チームの会話に混ざりたいから。

JS-6  手を止める日があるとき、ゲーム上の不利を心配したくない。
      生活のリズムを道具に決められたくないから。
```

## 3. 設計原則

```
1. 仕事に不利益を生む報酬設計をしない        ← 過正当化・時間的DP
2. 量ではなく多様性と継続の質を讃える         ← Goodhart・社会的DP
3. 自律性を1つは必ず残す                    ← SDT（最も欠けている）
4. 起点になる画面だけをナビに置く            ← Progressive Disclosure
5. 事実だけを述べ、煽らない                  ← 正典 + Zagal
6. 真実は操作の隣に出す                      ← Nielsen #1
7. 嘘のアフォーダンス・嘘の安心を置かない      ← Nielsen #2
```

## 4. 実装

### 4.1 骨格

```
┌─ AppShell（遷移をまたいで生存する1枚）
│  [≥768px] サイドバー   [<768px] ☰ → MobileNavDrawer（中身は同一）
│  ├ PendingGrantBanner    課金の反映待ち
│  ├ TrackingStatusBanner  追跡停止（App未導入）— blue/情報トーン
│  └ ページ本体
│     └ ConsoleTopbar（sticky）プロンプト + 🪙/💎 + ルーン購入(+)
└─ RewardModalHost  どの入口からでも報酬が出迎える
```

認証判定は `(shell)/(authed)/layout.tsx` の `AuthGate` に1箇所集約。

### 4.2 ナビゲーション（原則4）

**セッションの起点になる画面だけ**を置く。6項目。

```
NAVIGATION                     SHOP
⌂ ~/home       JS-1, JS-2      $ ~/shop   ← 琥珀はここだけ
@ ~/@username  JS-5
◆ ~/monsters   JS-4の起点
≡ ~/summon     JS-3
▲ ~/leaderboard JS-5
```

起点にならない画面は**廃止せず、必要になる文脈から入る**（Progressive Disclosure）:

| ページ | 入口 |
|---|---|
| items | monsters の素材ストリップ |
| badges・mints | 自分のプロフィールのバッジ壁・プレート棚 |
| pass | shop のタブ |
| forge | monsters の ⚒ バッジ / スキン詳細 |
| summon/limited | summon ページ内リンク |
| mypage/billing | HERO_STATUS メニュー |

### 4.3 導線（Job Stories 対応）

| JS | 実装 |
|---|---|
| JS-1 | シェルの `RewardModalHost` がどの入口でも発火 |
| JS-2 | `NextActionStrip`「召喚 ×N ぶんのコインがあります」（コストは開示APIから取得） |
| JS-3 | 召喚結果の `NEW` チップ → 「図鑑で確認 →」→ 図鑑で直近24hに `NEW` |
| JS-4 | monsters カード →「このモンスターのスキンを見る」→ `/shop/skins?monster=slug` |
| JS-5 | leaderboard の自分ハイライト（YOU）→ プロフィール |
| JS-6 | **ストリークは週末で途切れない**（BE #305）+ ルールを home で開示 |

### 4.4 表示の規律

| 規律 | 実装 |
|---|---|
| 真実は操作の隣（原則6） | `InlineActionResult`（トーストは不採用） |
| 資金不足はコイン/ルーンで非対称 | コイン=「PRをマージして集めましょう」購入導線なし / ルーン=`/shop/runes` |
| 空状態は次の行動を示す | `ConsoleEmptyState`（CTAは名声圏のみ） |
| 値を仮置きしない | `TermLoading`（端末出力行）。価格は `—`。召喚コストもAPI由来 |
| 嘘を置かない（原則7） | 「click to equip」削除 / ACTIVE→TRACKING・OFFLINE / [E]キーは実装 |
| 色の専有 | 琥珀=課金 / gold=SSR / blue=システム情報 / 緑=名声 |

## 4.5 課金導線（demand-first）

この製品は課金で成り立つ。**売らないことは設計の美点ではない**。
ただし煽って売ることはしないので、代わりに「**欲しくなった地点に、価格と経路を置く**」を徹底する。

原則:

```
D1. 需要が先、提示は後。欲しい対象（相棒・天井・スキン）を見ている地点にだけ置く
D2. 事実だけを置く。数値と行き先のみ。残り時間・在庫演出・偽の限定は置かない
D3. 名声圏の空白を突いて売らない（図鑑の未発見・バッジ未達は売り場ではない）
D4. コインは売らない。コインは仕事の対価であり、買えると壊れる
D5. 隠している価値は無いのと同じ。加入者だけに効いている恩恵は未加入者にも数値で見せる
```

実装:

| 需要が生まれる地点 | 置いたもの |
|---|---|
| 天井カウンターを見ている（＝あと何回引くか考えている） | `PityMeter` に「パス加入中は天井 60 回（10回少ない）」+ `/pass`（未加入時のみ／D5） |
| 相棒に愛着が湧いた | monsters カードのスキン棚。**既にスキンを着せている相棒でも出す**（最も買う層を隠していた） |
| ルーン残高を見た | `mypage/billing` のウォレットに補充導線。ルーンは購入でしか増えないため |
| ショップの棚が空だった | 別の棚へ案内（行き止まりにしない） |
| ルーン不足で操作が止まった | `BalanceShortfall` の購入導線（既存） |
| コイン不足で操作が止まった | 購入導線を出さない。「PRをマージして集めましょう」のみ（D4） |

**やらないこと**: home への常設バナー（需要より先に出る）/ 召喚失敗直後の販売（欠乏の演出）/
ストリーク保護の販売（時間的ダークパターン）/ コインの販売。

## 5. 未解決（設計判断が必要）

### 5.1 リーダーボードの軸（原則2に抵触）

XP = マージPR数 × 100。つまり**同僚のPR本数の公開順位表**。

- Zagal分類の social dark pattern（社会的比較の圧力）
- Goodhart の法則: PR数は生産性の代理指標として不適切で、指標化すれば最適化される（PRを刻む）
- 上司が評価に流用するリスク

**提案**: 廃止ではなく軸の変更。図鑑の発見数・バッジTier・マスタリーなど
「量」ではなく「多様性・継続の質」へ。SDTの関係性は満たしつつ直接比較の毒を抜く。

### 5.2 自律性の欠如（原則3・SDTで最も弱い）

有能感（Lv・図鑑・バッジ）と関係性（リーダーボード）はあるが、**自律性がほぼ無い**。
報酬は自動で降り、ユーザーが選べるのは相棒とスキンだけ。

**提案**: 「今月の目標を自分で決める」（図鑑を埋める / 特定属性を育てる 等）。
既存データのみで実装でき、外的報酬を増やさずに自律性を満たせる。

### 5.3 長期休暇でストリークが切れる

週末は #305 で解決したが、長期休暇は依然リセットされる。
猶予日数（grace）か直近N日の窓ベースへの変更が次の一手。

### 5.4 マスタリーの物語矛盾

正典 `profile.html` は殿堂カードを「買っただけでは入れない、St10まで**使い込んだ記録**」と
記述しているが、実装は**ルーンで購入して上げる**。配置ではなく思想の不一致。

トーストライブラリ / 打鍵アニメ / ルーン残高の概数表示（前払式支払手段の透明性）/
