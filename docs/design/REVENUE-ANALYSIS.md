# 収益構造の分析（2026-07 時点）

UXの最終目標は売上である。この文書は「今の実装で、誰が、何に、いくら払えるのか」を
コードから読み取った事実だけで書く。推測には(推測)と明記する。

関連: `UX-DESIGN.md`（設計思想）/ `UX-IMPROVEMENT-PLAN.md`（施策履歴）

## 0. 結論

**売上が立たない主因は導線ではない。「売るもの」と「戻ってくる理由」が実装されていない。**

3つの事実:

1. **スキンは 0 件配信**。`monsterSkinSeedCatalog(): List<MonsterSkin> = emptyList()`
   （`ExposedDatabaseConfig.kt:744`）。課金の中心に据えた美容課金の在庫がゼロ。
2. **通常召喚（コイン）からモンスターは出ない**。通常プールの中身は魂パックと進化素材だけ
   （`ExposedDatabaseConfig.kt:649-667`）。ガチャがコレクションに繋がっていない。
3. **戻ってくる理由が1つも実装されていない**。メール・プッシュ・ユーザー向け通知は両リポジトリに存在しない
   （Slack通知は運用アラート専用 `SlackBillingAlertNotifier.kt`）。

直近の #138〜#141 は店の外装を整える作業だった。棚に商品が無い状態でそれをやっていた。

## 2. ルーンの使い道 — 設計と実態

| 使い道 | 価格 | 実際に買えるか |
|---|---|---|
| 限定召喚 | 30/回（10連も300、割引なし） | ○ 対象モンスターは`seasonal-debugger` **1体のみ**・3%・天井60(パス50) |
| ルーン魂パック | 30 / 80 / 210 | ○ 6属性×3サイズ=18SKU |
| 記念プレート | 200 | ○ ただし条件が100PR / Lv100 / 図鑑完成 |
| バッジ工房（BADGE track） | 累計2,496 | ○ |
| **スキン** | 320 / 880 / 1,800 | **× 0件** |
| **モンスター工房（MONSTER track）** | 累計6,000 | **× スキン必須なので使えない** |

設計上いちばん大きい2つの吸収先（スキン最大1,800×体数、工房6,000）が**まるごと死んでいる**。
FE側のスキン画面・工房のマスタリー機構（`SkinMasteryPanel` 等）は完成しているが入力が無い。

**今日いちばん機能している課金は、ルーン魂パックの為替差**である:
コイン版は3,000コインで30魂、ルーン版は210ルーンで450魂。**魂あたり15倍**効率が良い。
450魂をコインで買うと45,000コイン＝PR450件。ここは実際に効いている(推測: 未計測)。

## 3. 無料通貨（コイン）— なぜ16,475コインが使われずに残るのか

**獲得**: PRマージ 100（大規模+50 / 7日ストリーク+300）。
1日3件までが100%、4〜10件は50%、11件以降は0%（`HandlePrMergedUseCase.kt:550-587`）。
※このPR件数による減衰はFEでどこにも開示されていない。

**使い道**: 通常召喚 300/3,000、コインショップ6SKU（魂パック3種・進化素材3種）。

つまり**コインで買えるものは、モンスターを育てている人にしか価値が無い**。
そして——

**モンスターはPRマージ時に配られる。ガチャからは出ない。**
`HandlePrMergedUseCase.kt:189-219` → `MonsterSelector.selectMonster` は
`SHA256(prNodeId) % monsters.size` の**フラットな1/57**。レアリティ重みは無い
（`MonsterSelector.kt:28-35`）。SSRの確率＝SRの確率。

結果:
- 召喚しても図鑑は埋まらない → 召喚する動機が弱い → コインが余る
- レアリティに信号が無い → 特定の1体に愛着が湧きにくい → スキンを買う動機が育たない

16,475コインの滞留は不具合ではなく、**この構造の正しい帰結**である。

## 4. 無料ユーザーがモンスターを手に入れる唯一の経路

1. GitHub OAuth ログイン
2. GitHub App をインストール（外部・github.com）
3. 対象リポジトリで PR を出して**マージされる**（他人依存・待ち時間は制御不能）
4. Webhook → モンスター1体付与

**スターター付与・チュートリアルモンスター・無料ガチャは存在しない**
（signup/firstLogin/initialGrant の実装なし。dev用 `GrantResourcesUseCase` もモンスターは配らない）。

そして `FirstQuestChecklist` のステップ3「最初の相棒モンスターを迎える」のCTAは `/summon` を指しているが、
**通常召喚からモンスターは出ないので、このCTAではステップ3を達成できない**
（`FirstQuestChecklist.tsx:51-52`）。

課金でモンスターを得る唯一の道は限定召喚の`seasonal-debugger`（3%）。
天井まで引くと 60回×30 = 1,800ルーン ≒ **¥4,700**（パスなら1,500ルーン ≒ ¥3,900）。

## 5. 収益をゼロにしうる設定不備

`NEXT_PUBLIC_GITHUB_APP_SLUG` が未設定のとき:

- `page.tsx:51` → インストールボタンが `href="#"`（押しても何も起きない）
- `page.tsx:149` → `https://github.com/apps//installations/new`（404）
- `TrackingStatusBanner` / `FirstQuestChecklist` → リンクを出さない

リポジトリに `.env.example` が無く、この変数はどこにも記載されていない。
**App が入らなければ PR は追跡されず、コインもモンスターも発生せず、課金の動機も生まれない。**
本番値の確認が最優先（コードからは確認できない）。

## 6. パスの実装リスク

150ルーン/月の付与は **PSPのwebhook到着時にしか発火しない**
（`HandleSubscriptionWebhookUseCase.kt:133-136, 256-275`）。内部スケジューラは無い。
PSPが期間更新webhookを送らなければ、課金は継続しているのにルーンが届かない。
解約要因かつ前払式支払手段としての表示問題になりうる。

副次: 通常召喚の**ソフト天井はパスで短縮されない**（60固定 / `GachaSampler.kt:23`）。
パス保有者は soft60→hard70 の10回しかブーストが乗らず、未加入者の20回より窓が狭い。

## 7. 計測が無い

両リポジトリに解析基盤が無い（gtag / posthog / mixpanel / amplitude / sentry いずれも0件）。
**課金到達率・離脱地点・召喚回数を一切計測できない。**
以降のUX判断は全部が推測になる。#138〜#141 の効果も測れない。

## 8. 優先順位（売上への距離が近い順）

### P0 — 前提を直す
1. `NEXT_PUBLIC_GITHUB_APP_SLUG` の本番値を確認。未設定なら流入がゼロ。
   併せて壊れたリンク（`href="#"` / 空slug URL）を描画しないようにする
2. **通常召喚プールにモンスターを入れる（レアリティ重み付き）**。
   コインに欲しい使い道が生まれ、召喚が図鑑に繋がり、滞留コインが動き、愛着が生まれる。
   スキンもパスも限定召喚も、すべてこの上に乗っている
3. PRマージのモンスター抽選をレアリティ重み付きにする（現状フラット1/57でSSRが特別でない）
4. パスのルーン付与を内部スケジューラで担保する（webhook欠落で未付与になる）

### P1 — 売るものを実在させる
5. **スキンを配信する**。数体でも出れば 320/880/1,800 の吸収先と工房6,000が同時に開き、
   既に作ってある demand-first 導線が初めて機能する。ボトルネックは実アート＝事業判断
6. 限定プールを1体から増やしてローテーションさせる

### P2 — 戻ってくる理由を作る
7. **PRマージ時の外部通知を1本**。GitHub webhookで「いつ嬉しいか」を既に知っているので、
   その瞬間にSlack DM/メールで「◆ Fire Dragon を迎えました」を送るのが最も費用対効果が高い。
   これは Job Story JS-1 そのもので、現状これを満たす手段が存在しない

### P3 — 測る
8. 最小の計測（召喚実行 / ショップ表示 / チェックアウト開始 / 完了）。
   これが無い限り、以降の改善は当て推量のまま

## 9. この分析で変わらないもの
